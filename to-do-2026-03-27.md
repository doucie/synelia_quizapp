# PARTIE A — Nettoyage et corrections de la BD existante

## A.0 Tables `_seq` : explication et suppression

### Pourquoi ces tables existent ?

Toutes les entités (sauf `Decision` et `EmailVerificationToken`) utilisent `@GeneratedValue(strategy=GenerationType.AUTO)`.

Dans **Hibernate 6+** (Spring Boot 3.x), `GenerationType.AUTO` pour MySQL ne map plus vers `AUTO_INCREMENT` mais vers une **stratégie TABLE** : Hibernate crée une table `xxx_seq` avec un compteur `next_val` pour générer les IDs.

Résultat : pour chaque table, une table `_seq` fantôme est créée. Ça fait 18 tables inutiles.

### La solution

Changer `GenerationType.AUTO` → `GenerationType.IDENTITY` dans les 18 entités. `IDENTITY` utilise le `AUTO_INCREMENT` natif de MySQL. 0 table `_seq` créée.

# PARTIE B — Versioning des formulaires

## Analyse architecturale

### Le problème

Un recruteur crée une campagne avec des questions. Des candidats répondent. Le recruteur veut modifier les questions. Il faut que les anciens candidats gardent leurs réponses intactes.

### La solution retenue : versioning au niveau formulaire uniquement

On ne fait PAS de versioning au niveau question. Voici pourquoi :

1. **`form_version`** est le point de verrouillage unique. Quand un candidat répond, la form_version est lockée.
2. Quand le recruteur modifie un formulaire locké, on crée une **nouvelle form_version**. Les questions inchangées sont **reliées** (pas copiées) à la nouvelle version via `form_questions`. Seules les questions modifiées sont **dupliquées** (nouvelle ligne en BD avec un `question_ref` commun pour traçabilité).
3. La table `form_questions` (many-to-many entre form_version et question) permet qu'une même question soit dans plusieurs versions/formulaires sans duplication inutile.
4. Les réponses sont directement liées à une question (comme déjà fait). Si une question est dupliquée, ses réponses sont aussi dupliquées.

**Avantage** : un seul point de lock, pas de double versioning, les questions non modifiées ne sont pas dupliquées.

### Pourquoi PAS de table `question` séparée de `question_version`

ChatGPT a proposé `question(id, question_ref)` + `question_version(id, question_id, ...)` pour séparer l'identité logique des versions. Mais :

- Ça ajoute une jointure à CHAQUE requête pour zéro bénéfice
- Le regroupement des versions d'une même question se fait aussi bien avec un simple champ `question_ref` (UUID) dans la table question
- En pratique, quand on charge un formulaire, on a besoin des questions concrètes, pas d'une abstraction "identité logique"

### Pourquoi PAS de `campaign_forms` (table pivot)

Un formulaire appartient à UNE campagne (FK `campaign_id` dans `form`). Un formulaire n'est pas partagé entre campagnes — si on veut le même formulaire dans 2 campagnes, on le copie. Ça évite les effets de bord (modifier le form d'une campagne impacterait l'autre).

# B.2 Table `form_version`

[x] Créer la table et le stack Java complet

```sql
CREATE TABLE form_version (
  id              INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  form_id         INT UNSIGNED NOT NULL,
  version_number  INT NOT NULL DEFAULT 1,
  is_published    BIT DEFAULT 0,
  is_locked       BIT DEFAULT 0,
  -- colonnes communes
  created_at      DATETIME DEFAULT CURRENT_TIMESTAMP,
  created_by      INT UNSIGNED,
  updated_at      DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  updated_by      INT UNSIGNED,
  is_deleted      BIT DEFAULT 0,
  search_string   TEXT,
  CONSTRAINT fk_form_version_form FOREIGN KEY (form_id) REFERENCES form(id)
);
```

**Règles de lock :**
* `is_locked` = false par défaut
* Passe à true dès qu'un candidat **soumet** son quiz avec cette version
* Si `is_locked = true` : AUCUNE modification possible (questions, réponses, configuration)
* Pour modifier : créer une nouvelle `form_version` (version_number + 1)

**Règles de publication :**
* UNE SEULE version peut avoir `is_published = true` par formulaire
* Publier une version dépublie automatiquement la précédente
* Les candidats en cours de quiz gardent leur version initiale
* Les nouveaux candidats reçoivent la version publiée

# B.3 Table `question`

[x] Créer la table et le stack Java complet

```sql
CREATE TABLE question (
  id               INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  question_ref     VARCHAR(36),
  question_text    TEXT NOT NULL,
  question_chrono  INT UNSIGNED DEFAULT 10,
  question_type    VARCHAR(20) DEFAULT 'SINGLE_CHOICE',
  score            INT DEFAULT 1,
  difficulty_level VARCHAR(20),
  speciality_id    INT UNSIGNED,
  -- colonnes communes
  created_at       DATETIME DEFAULT CURRENT_TIMESTAMP,
  created_by       INT UNSIGNED,
  updated_at       DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  updated_by       INT UNSIGNED,
  is_deleted       BIT DEFAULT 0,
  search_string    TEXT,
  CONSTRAINT fk_question_speciality FOREIGN KEY (speciality_id) REFERENCES specialities(id)
);
```

**Colonnes expliquées :**
* `question_ref` (VARCHAR 36) — UUID optionnel. Quand une question est dupliquée (parce qu'on la modifie dans un formulaire locké), la copie garde le même `question_ref` que l'originale. Permet de tracer "cette question est une version de celle-là". NULL si pas de lignée.
* `question_text` — contenu de la question (ancien `question_content`)
* `question_chrono` — durée en secondes (existait dans `questions`)
* `question_type` — ENUM : SINGLE_CHOICE, MULTIPLE_CHOICE, TRUE_FALSE, TEXT (existait dans `questions`)
* `score` — points pour cette question (NOUVEAU, utile pour le barème)
* `difficulty_level` — EASY, MEDIUM, HARD (NOUVEAU, pour les badges front)
* `speciality_id` — FK vers specialities (existait dans `questions`)

**Relation many-to-many** : une question peut être dans PLUSIEURS form_versions (via `form_questions`). Un même formulaire peut avoir plusieurs questions. Quand une question n'est pas modifiée entre deux versions, elle est simplement RE-LIÉE (pas copiée).

```sql
CREATE TABLE form_questions (
  id                  INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  form_version_id     INT UNSIGNED NOT NULL,
  question_id         INT UNSIGNED NOT NULL,
  question_order      INT DEFAULT 0,
  chrono_override     INT UNSIGNED,
  -- colonnes communes
  created_at          DATETIME DEFAULT CURRENT_TIMESTAMP,
  created_by          INT UNSIGNED,
  updated_at          DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  updated_by          INT UNSIGNED,
  is_deleted          BIT DEFAULT 0,
  search_string       TEXT,
  CONSTRAINT fk_fq_form_version FOREIGN KEY (form_version_id) REFERENCES form_version(id),

  UNIQUE KEY uk_fq_version_question (form_version_id, question_id)

```

**Colonnes expliquées :**
* `question_order` — ordre d'affichage de la question dans cette version de formulaire (existait dans `campaign_questions.order`)

**Pourquoi cette table ?**
* Une question peut être dans plusieurs form_versions (quand elle n'est pas modifiée entre deux versions)
* L'ordre d'affichage peut varier selon le formulaire
* Le chrono peut être surchargé par formulaire
