### P19 — Corriger le désalignement curseur / caractères dans les éditeurs (textarea-mirror + RTE)

**Contexte :**
L'ajout de badges colorisés sur les `{{variables}}` (P16) a introduit deux bugs d'édition distincts :

**Bug A — Mode HTML source (désalignement curseur)**
Le mode HTML source utilise un pattern textarea-mirror : une `<textarea>` transparente (z-index 1) est superposée à un `<pre>` de coloration syntaxique (z-index 0). Les deux doivent avoir un rendu caractère-par-caractère identique pour que la position visuelle du curseur dans le `<pre>` corresponde exactement à la position réelle du caret dans la `<textarea>`. Si les spans de coloration dans le `<pre>` ont du `padding` ou une `border`, ils sont plus larges que le texte brut dans la `<textarea>`. Chaque `{{variable}}` ajoute alors ~8 px de décalage cumulatif : le curseur semble être à une position mais l'action (espace, suppression) s'applique à un autre endroit.

La règle fondamentale du textarea-mirror : **ne jamais modifier la largeur de rendu** des spans dans le `<pre>` par rapport au texte brut. Seules `color`, `background-color`, `font-weight`, `font-style`, `text-decoration` et `box-shadow` sont sûres. `padding`, `margin`, `border`, `letter-spacing` et `word-spacing` sont prohibés.

**Bug B — Mode WYSIWYG (curseur à l'intérieur du span)**
Dans le RTE contenteditable, les spans `.rte-var` qui encapsulent `{{key}}` sont éditables par défaut. Cliquer sur un badge place le curseur *à l'intérieur* du placeholder entre les accolades, puis taper ou supprimer agit sur le contenu littéral `{{key}}` plutôt que sur le texte autour. La solution est de rendre ces spans atomiques via `contenteditable="false"`, comme des chips non éditables.

**Correctifs apportés (9 mai 2026) :**
- [x] 🔴 Dans `email-editor.scss`, supprimer `padding` et `border` de `.token-placeholder`. Utiliser `box-shadow: 0 0 0 1px color-mix(...)` pour l'effet de bordure visuelle (pas de layout, pas de désalignement). La `background` seule suffit à identifier les variables dans le `<pre>`.
- [x] 🔴 Dans `rich-text-editor.ts`, `colorizeVariablesInHtml()` : ajouter `contenteditable="false"` sur les spans `.rte-var` générés, pour qu'ils soient des chips atomiques non éditables.
- [x] 🔴 Dans `rich-text-editor.ts`, `insertVariable()` : ajouter `contenteditable="false"` sur le span inséré par `execCommand('insertHTML')`.
- [x] 🔴 Dans `rich-text-editor.ts`, `onInput()` : avant d'émettre la valeur via `valueChange`, dépouiller les spans `.rte-var` du HTML et restaurer `{{key}}` brut. Ainsi le template stocké en base ne contient que des `{{key}}` propres, sans balises de présentation. C'est aussi plus robuste car le backend email renderer n'a pas à gérer des `<span>` parasites.

**Tâches complémentaires encore à faire :**
- [ ] 🟡 Vérifier qu'en mode `email-document` (template complet), la restauration `{{key}}` dans `onInput()` n'altère pas le `emailDocumentShell` (prefix/suffix) ni le corps extrait par `extractEditedEmailBody()`. Écrire un test manuel : saisir du texte, insérer `{{title}}`, sauvegarder, recharger — le template en base ne doit pas contenir de `<span class="rte-var">`.
- [ ] 🟡 Vérifier la règle textarea-mirror après chaque futur ajout de style sur `.token-placeholder` ou sur les tokens de coloration syntaxique en général : documenter dans `email-editor.scss` que `padding`, `border` et `margin` sont interdits sur tout span à l'intérieur de `.source-editor-highlight`.

- [ ] 🟡 Valider que les spans `contenteditable="false"` dans le RTE se comportent bien au clavier : `Tab` / `Shift+Tab` autour d'un chip, `Backspace` avant un chip (doit supprimer le chip entier, pas son dernier caractère), `Delete` après un chip (doit supprimer le chip entier).

Quand un développeur écrit `{{maVariable}}` dans le champ "Contenu principal" du template, la variable n'est pas automatiquement reconnue comme une "variable créée" dans `userDefinedVariableKeys`. Il est obligé de d'abord cliquer manuellement sur "Créer" pour déclarer la variable avant qu'elle soit reconnue et colorisée.

Ce comportement est contre-intuitif : si un pattern `{{key}}` apparaît dans le contenu éditable mais n'est pas dans les listes connues (`EDITABLE_VARIABLE_DEFINITIONS`, `GLOBAL_SYSTEM_VARIABLE_KEYS`, variables métier de `readonlyVariableGroups()`), il devrait être auto-détecté et proposé comme "variable créée" sans action manuelle.

**Ce qu'il faut faire :**
- [x] 🟡 Dans `email-editor.ts`, scanner les valeurs actuelles des champs éditables (en particulier `editableVariables().content`, et tous les champs de type `richtext` ou `text`) pour extraire les patterns `{{key}}` inconnus des listes de variables système.
- [x] 🟡 Ajouter automatiquement ces clés détectées à `userDefinedVariableKeys` (via `effect()` ou `computed()` réactif sur `editableVariables()`).
- [x] 🟡 Éviter les doublons : ne pas ajouter une clé déjà présente dans `GLOBAL_SYSTEM_VARIABLE_KEYS`, `EDITABLE_VARIABLE_DEFINITIONS` ou `readonlyVariableGroups()`.
- [x] 🟡 Déclencher cette détection à chaque changement de `editableVariables()` pour rester en sync avec le contenu tapé.

### P21 — Bg/border manquants sur les badges variable lors de l'insertion dans "Contenu principal"

**Contexte :**
Après l'insertion d'une variable via la toolbar du RTE dans le champ "Contenu principal", la couleur du texte du badge `{{key}}` s'applique correctement, mais le `background-color` et le `box-shadow` (bordure visuelle) n'apparaissent pas immédiatement. Ils ne s'affichent que lorsqu'un autre champ (ex: TITRE, SOUS-TITRE) est modifié.

**Cause probable :** `colorizeVariablesInHtml()` est appelé à l'initialisation du RTE (`writeValue()` / `ngOnChanges`) mais pas après `insertVariable()`. Quand `insertVariable()` insère un `<span class="rte-var">` via `execCommand('insertHTML')`, le span est inséré avec la couleur correcte (issue de l'HTML injecté) mais sans le re-passage complet par la colorisation. Le `(valueChange)` déclenche un update du signal parent, mais `ngOnChanges` ne se re-déclenche que si la référence de `variableGroups` change.

**Ce qu'il faut faire :**
- [ ] 🟡 Dans `rich-text-editor.ts`, après l'appel `execCommand('insertHTML', ...)` dans `insertVariable()`, appeler immédiatement `colorizeVariablesInHtml()` sur le `innerHTML` courant du contenteditable, et ré-appliquer le résultat en préservant la position du curseur (sauvegarder/restaurer la sélection via `Range` avant/après).
- [ ] 🟡 Vérifier que `colorizeVariablesInHtml()` est accessible depuis `insertVariable()` (même classe) et reçoit les `variableGroups` courants.
- [ ] 🟡 Vérifier que la restauration de sélection après colorisation ne provoque pas de désalignement curseur (cf. règles P19 : aucun `padding`/`border` sur les spans à l'intérieur d'un textarea-mirror).

### P23 — Coloriser les `{{variables}}` dans les `<input>` de preview-variable-section (sans bg/border)

**Contexte :**

Contraintes spécifiques aux inputs (différentes du RTE) :
- Un `<input>` ne supporte pas le contenu HTML — impossible d'y insérer des `<span>` colorisés

- [x] 🟡 Appliquer la colorisation `{{key}}` sur ce div via une fonction légère similaire à `colorizeVariablesInHtml()`, mais en configurant les spans générés pour n'avoir **que** `color` sans aucun `background`, `box-shadow` ni `border`.
- [x] 🟡 Gérer la valeur brute : quand `(input)` déclenche un changement, extraire le texte brut en restaurant `{{key}}` (strip les spans, comme dans `onInput()` du RTE) avant d'émettre vers `ngModel`.
- [x] 🟡 Gérer le placeholder : afficher via `::before` + `attr(data-placeholder)` quand le div est vide.
- [x] 🟡 Forcer la saisie sur une ligne : `overflow: hidden; white-space: nowrap` + `(keydown.enter)` → `$event.preventDefault()`.

### P24 — Adapter les presets email au mode dark/light (dashboard preview + clients mail)

**Contexte :**

Aucun bloc `@media (prefers-color-scheme: dark)` n'existe dans leur `<style>`. Deux problèmes découlent de ce manque :

**Problème A — Dashboard (`/dashboard/email-presets/`)** : La preview iframe est rendue par `buildPreviewDocument()` → `applyPreviewThemeMode()` → `rewritePreferredColorSchemeStyles()` (email-editor.ts lignes 2136–2280). Cette infrastructure est déjà correctement connectée : `uiThemeMode` est un signal mis à jour via `uiThemeService.isDarkMode$`, et `updatePreview()` est déjà appelé dans `ngOnInit` quand le thème change (ligne 722). **Mais** comme les presets n'ont aucun bloc `@media (prefers-color-scheme: dark)`, `rewritePreferredColorSchemeStyles()` ne trouve rien à extraire → `forcedCss` reste vide → aucun changement visuel en mode dark. L'infrastructure frontend est correcte, il manque uniquement le CSS dark dans les templates HTML.

Sans ces blocs dans le HTML, l'email s'affiche toujours en mode clair — ou pire, certains clients tentent une inversion automatique des couleurs qui donne un résultat illisible.
