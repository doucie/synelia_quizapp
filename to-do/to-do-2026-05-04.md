### P15 — Corriger le formatage CSS en présence de placeholders `{{variable}}`

Stocker la table de correspondance token → placeholder original.

- [x] 🔴 Vérifier que la restauration est faite avant le `join('\n')` final, de sorte que `highlightCssLine()` reçoive les `{{...}}` en une seule pièce et puisse les coloriser correctement via `highlightInlinePlaceholders()`.

### P19 — Corriger le désalignement curseur / caractères dans les éditeurs (textarea-mirror + RTE)

**Contexte :**
L'ajout de badges colorisés sur les `{{variables}}` (P16) a introduit deux bugs d'édition distincts :

**Bug A — Mode HTML source (désalignement curseur)**
Le mode HTML source utilise un pattern textarea-mirror : une `<textarea>` transparente (z-index 1) est superposée à un `<pre>` de coloration syntaxique (z-index 0). Les deux doivent avoir un rendu caractère-par-caractère identique pour que la position visuelle du curseur dans le `<pre>` corresponde exactement à la position réelle du caret dans la `<textarea>`. Si les spans de coloration dans le `<pre>` ont du `padding` ou une `border`, ils sont plus larges que le texte brut dans la `<textarea>`. Chaque `{{variable}}` ajoute alors ~8 px de décalage cumulatif : le curseur semble être à une position mais l'action (espace, suppression) s'applique à un autre endroit.

La règle fondamentale du textarea-mirror : **ne jamais modifier la largeur de rendu** des spans dans le `<pre>` par rapport au texte brut. Seules `color`, `background-color`, `font-weight`, `font-style`, `text-decoration` et `box-shadow` sont sûres. `padding`, `margin`, `border`, `letter-spacing` et `word-spacing` sont prohibés.

**Bug B — Mode WYSIWYG (curseur à l'intérieur du span)**
Dans le RTE contenteditable, les spans `.rte-var` qui encapsulent `{{key}}` sont éditables par défaut. Cliquer sur un badge place le curseur *à l'intérieur* du placeholder entre les accolades, puis taper ou supprimer agit sur le contenu littéral `{{key}}` plutôt que sur le texte autour. La solution est de rendre ces spans atomiques via `contenteditable="false"`, comme des chips non éditables.

**Correctifs apportés (9 mai 2026) :**
- [x] 🔴 Dans `email-editor.scss`, supprimer `padding` et `border` de `.token-placeholder`. Utiliser `box-shadow: 0 0 0 1px color-mix(...)` pour l'effet de bordure visuelle (pas de layout, pas de désalignement). La `background` seule suffit à identifier les variables dans le `<pre>`.
- [x] 🔴 Dans `rich-text-editor.ts`, `colorizeVariablesInHtml()` : ajouter `contenteditable="false"` sur les spans `.rte-var` générés, pour qu'ils soient des chips atomiques non éditables.
- [x] 🔴 Dans `rich-text-editor.ts`, `insertVariable()` : ajouter `contenteditable="false"` sur le span inséré par `execCommand('insertHTML')`.
- [x] 🔴 Dans `rich-text-editor.ts`, `onInput()` : avant d'émettre la valeur via `valueChange`, dépouiller les spans `.rte-var` du HTML et restaurer `{{key}}` brut. Ainsi le template stocké en base ne contient que des `{{key}}` propres, sans balises de présentation. C'est aussi plus robuste car le backend email renderer n'a pas à gérer des `<span>` parasites.

**Tâches complémentaires encore à faire :**
- [ ] 🟡 Vérifier qu'en mode `email-document` (template complet), la restauration `{{key}}` dans `onInput()` n'altère pas le `emailDocumentShell` (prefix/suffix) ni le corps extrait par `extractEditedEmailBody()`. Écrire un test manuel : saisir du texte, insérer `{{title}}`, sauvegarder, recharger — le template en base ne doit pas contenir de `<span class="rte-var">`.
- [ ] 🟡 Vérifier la règle textarea-mirror après chaque futur ajout de style sur `.token-placeholder` ou sur les tokens de coloration syntaxique en général : documenter dans `email-editor.scss` que `padding`, `border` et `margin` sont interdits sur tout span à l'intérieur de `.source-editor-highlight`.
