# Pipeline configurable par campagne + flux par défaut + refonte permissions

> **Objectif** : Remplacer le flux de recrutement rigide en 3 étapes codées en dur
> (Candidature → Pré-sélection → Décision finale) par un **pipeline configurable**
> permettant à chaque campagne de définir ses propres étapes.
> Ajout d'un système de **templates de pipeline** pour définir un flux par défaut.
> **Refonte complète du système de permissions** : rôles système (SUPER_ADMIN/ADMIN/UTILISATEUR), groupes métiers customisables, surcharges individuelles, permissions par entité.
>
> **Contexte technique** :
> - Backend : Spring Boot 3.5.6, Java 21, Hibernate 6.6.x, MySQL 8.0.43, Flyway
> - Frontend : Angular 20.2.0, Standalone components, Signals/Computed, SCSS
> - Migrations existantes : V1_001 → V1_007
> - Architecture pipeline : **3 tables** (`pipeline_template`, `pipeline_stage`, `application_progress`)
>   - Chaque campagne pointe vers un `pipeline_template` (FK obligatoire)
>   - Si besoin d'un flux custom → dupliquer le template
>   - Pipeline **verrouillé** (`is_locked`) dès qu'un candidat a un progrès dessus
>   - Changement de pipeline en cours de campagne → migration sélective des candidats compatibles
> - **Convention API** : tout en POST (sécurité : pas de paramètres dans l'URL/logs, pas de caching accidentel)
> - **Convention update partiel** : `""` → ignorer (garder la valeur existante), `null` → mettre à null en BDD, autre → mettre à jour normalement
> - **Endpoints standard par controller** : `/create`, `/update`, `/delete`, `/getByCriteria`, `/getAllByCriteria`, `/updateAll`, `/updateDeleted`
> - Architecture permissions : **6 tables** (`system_role_permission`, `business_group`, `business_group_permission`, `user_business_group`, `user_permission_override`, `entity_permission`)
>   - Rôles système : SUPER_ADMIN (bypass total), ADMIN (plancher immuable), UTILISATEUR (fully overridable)
>   - Groupes métiers : customisables par entreprise, 0..n par user, indépendants du rôle système
> - Permissions actuelles (à remplacer) :
>   - `FunctionalityEnum` : enum CRUD par entité, passé partout mais **jamais vérifié** (checkUserAccess ne fait que valider user ≠ null)
>   - `@PreAuthorize` sur controllers : rôle brut (SUPER/ADMIN/RECRUITER)
>   - `CampaignCrud` / `InterviewCrud` : tables de booléens par user par entité (canUpdate, canDelete, etc.)
>   - Frontend : guards par rôle + sidebar filtrée par rôle (3 niveaux fixes)
> - Pipeline actuel codé en dur :
>   - `applicationStatus` (String) : PENDING → SUBMITTED → PRE_SCREEN_ACCEPTED/REJECTED → FINAL_ACCEPTED/REJECTED (+ variantes ARCHIVED)
>   - `Decision.decisionType` : PRE_SCREEN_ACCEPTED | PRE_SCREEN_REJECTED | FINAL_ACCEPTED | FINAL_REJECTED
>   - `CampaignCrud` : canAcceptPreScreen, canAcceptFinal (permissions figées)
>   - Frontend : `getStepStatus()` / `getStepDescription()` dans ApplicationsComponent + DecisionsComponent (3 étapes fixes)
>   - `track-application` : 5 étapes simulées, non connectées à l'API
>
> ---
>
> ### Architecture des permissions (nouveau)
>
> **Deux axes indépendants** :
> - **Rôle système** (`user_role`) : `SUPER_ADMIN`, `ADMIN`, `UTILISATEUR` — fixe, 1 par utilisateur, non customisable
> - **Groupe(s) métier** (`business_group`) : MANAGER, STAGIAIRE, DRH, etc. — customisable par entreprise, 0..n par utilisateur
>
> Un MANAGER peut être ADMIN, un autre MANAGER peut être UTILISATEUR → les deux axes sont **indépendants**.
>
> **Résolution des permissions** :
> 1. `SUPER_ADMIN` → **TOUTES les permissions** — bypass complet, immuable (rien à ajouter, rien à retirer)
> 2. Sinon : `system_role_permission(rôle)` ∪ `business_group_permission(groupes)` (union)
> 3. Appliquer `user_permission_override` :
>    - `GRANT` → ajouter la permission
>    - `DENY` → retirer la permission **SAUF** si c'est un droit de base ADMIN (plancher immuable)
> 4. `UTILISATEUR` : GRANT et DENY sans restriction
>
> **Protection par rôle système** :
> - `SUPER_ADMIN` : accès total, aucun override ne s'applique
> - `ADMIN` : permissions de base = plancher non retirable ; ajouts via groupe métier ou override GRANT ; override DENY ignoré sur les perms de base
> - `UTILISATEUR` : tout est modifiable (GRANT/DENY sans restriction)
>
> **`FunctionalityEnum`** = catalogue unique de toutes les permissions possibles.
> `entity_permission` remplace `CampaignCrud` / `InterviewCrud` pour les permissions par entité spécifique.
>
> **Tables** : `system_role_permission`, `business_group`, `business_group_permission`, `user_business_group`, `user_permission_override`, `entity_permission`
>
> **Exemple** : 10 Managers (groupe métier), dont 3 ADMIN et 7 UTILISATEUR (rôle système) :
> - 3 ADMIN : droits base ADMIN + droits groupe MANAGER
> - 7 UTILISATEUR : droits base UTILISATEUR + droits groupe MANAGER
> - Marie (UTILISATEUR + MANAGER) n'a pas le droit sur une page → 1 override DENY → effectif
> - Paul (ADMIN + MANAGER) : même override DENY → ignoré si c'est un droit de base ADMIN
